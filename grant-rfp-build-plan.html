Build a Cowork Skill called "Grant RFP Analyzer" that does the following:

Inputs:
1. Grant RFP text (pasted or uploaded PDF)
2. Org profile (one-page doc: mission, programs, past grants, key staff, financials summary)

Process:
- Extract from the RFP: funder name, deadline, required sections with word/page limits,
  evaluation criteria and weights (if listed), eligibility requirements
- For each evaluation criterion, score the org profile 1–5 on how well it matches,
  with a one-line justification
- Identify the 2–3 org strengths to lead with in the narrative

Output:
A structured match report with:
- Funder summary (name, deadline, total award, eligibility)
- Required sections list with word limits
- Scored criteria table (criterion | weight | org score | evidence)
- Top 3 differentiators to emphasize
- 2–3 gaps to address or reframe

Keep the output clean and scannable — this feeds directly into the narrative drafting step.
Test with a real RFP: download any open grant from grants.gc.ca or grants.gov and run it through.

Risk Analysis Failure Points & Mitigations
Scanned / image-based PDF
Claude reads no content; match report looks plausible but is entirely fabricated from nothing.
✦ Mitigation
Sub-build 1 outputs a "content detected" block listing the first 3 extracted sections. If blank, halt and instruct user to paste RFP text instead.
Missing evaluation criteria
RFP has no explicit criteria or weights — Claude infers them silently. Scored table looks authoritative but may be wrong.
✦ Mitigation
Flag entire criteria table [INFERRED]. Mandatory user review step before Sub-build 2 begins.
Buried eligibility disqualifier
Geographic restriction or org-type requirement buried in RFP text is missed. Full application drafted for an ineligible org.
✦ Mitigation
Sub-build 1 ends with a mandatory STOP block: all extracted eligibility requirements listed, user must confirm each one before narrative drafting begins.
Word limit silent overflow
Sections exceed RFP word limits. Output looks complete. Submission gets disqualified.
✦ Mitigation
Sub-build 2 appends [487 / 500 words ✓] or [⚠ 523 / 500 — OVER] after every section, plus a summary table at the top.
Flag fatigue / underuse
Too many [HUMAN: verify] flags → user stops reading them. Too few → fabricated claims slip into the submission.
✦ Mitigation
Flag rule: anything not directly sourced from the org profile gets flagged — not just things that "seem uncertain." Flag count shown at top of every narrative doc.
Budget narrative ≠ line-item numbers
Narrative says "$45,000 for staff" but budget sheet has $47,500. Funder catches the discrepancy — red flag.
✦ Mitigation
Sub-build 3 outputs a reconciliation table after generating the budget narrative — every dollar figure in the narrative alongside its source budget line item.
Section order mismatch
Assembled package has sections in the wrong order. Submission is penalised or outright rejected by the funder.
✦ Mitigation
Sub-build 3 outputs a section order checklist after assembly, mapping each section to its RFP label. Human verifies before submitting.
Stale org profile data
Org profile has 2-year-old financials. Claude uses them without knowing they're outdated. Funder may flag inconsistencies.
✦ Mitigation
Org profile template includes "Data current as of: ___". If blank, Claude flags every financial figure [HUMAN: confirm this is current].
